# mneme-llm 是如何工作的

[English](DESIGN.md) · **简体中文**

本文写给需要审阅、维护或移植 mneme-llm 的人：每个部分做什么、它遵守哪些规则、用到了哪些数字以及为什么、它在什么
情况下会失败，以及它目前还没有做到什么。本文描述的是 0.1.0 版本；文中提到某个常量时，该常量在代码里以相同的名字
存在。

第一次读请按顺序读。第 2 节和第 3 节给出全貌；第 4–11 节逐模块展开；其余部分讲安全、失败、成本、测试、设计背后
的取舍，以及已知的局限。

## 1. 用途

与人交谈的伴侣需要记住对方（事实、计划、发生过的事、对方的感受），知道每个对方对自己来说是谁，
并对每个对方都有属于自己的心情。大多数实现把两者都保存在一个模型的对话中，或者保存在与某个框架
绑定的格式里，因此更换模型就会丢失它们。mneme-llm 把它们保存在一个格式有文档记录的 SQLite 文件中，
并通过可与任何模型配合的层来完成它需要的每个判断，从而：

1. 同一个文件在任何项目中都能把相同的事实提供给任何模型；
2. 当某个服务缺失或不可用时，不会出问题；
3. 花钱的部分很小、经过测量，并且是可选的。

## 2. 整体结构

```
 ┌──────────────────────────── 宿主程序（任意模型） ────────────────────────────┐
 │  aprompt() 回复前            aobserve() 回复后           tools / MCP / CLI    │
 └────────────┬───────────────────────────────┬──────────────────────────────┬──────────┘
              │                               │                              │
        Mneme（__init__.py）：一个空间；构建各层，发起模型调用     tools.py, mcp.py, cli.py
              │                               │
   ┌──────────┴─────────┐          ┌──────────┴───────────┐
   │ 记忆（memory.py）   │          │ 心情（mood.py）      │      写入模型的提示词与回复
   │ 笔记、回忆          │          │ 数值 + 情绪          │      裁判所读到的一轮对话
   └──────┬─────────────┘          └──────────┬───────────┘      每个人与伴侣的关系
          │ meaning/（3 层）                │ decide/（3 层）
          │ 向量 → 词向量中心 → 统一语言    │ Luna → 微型 → 你的模型

   │ 存储（store.py）：一个 SQLite 文件，结构 1            │   providers.py, text.py, dates.py, i18n.py
   └───────────────────────────────────────────────────────┘
```

**分层。** 依赖只朝一个方向。`text`、`dates`、`i18n`、`providers`、`exchange`、
`store` 和 `meaning/vectors` 不导入其上的任何东西；`decide` 和 `meaning` 建立在
`providers` 之上；`memory` 使用 `meaning` 和 `store`；`mood` 使用 `decide` 的类型；
`relations` 使用 `store`、`dates` 和 `i18n`（心情对它一无所知：`Mneme` 把每个人的
权重交给心情）；`capture` 使用 `memory` 的书写规则；`Mneme` 把它们连接起来并负责
对模型的调用；`tools`、`mcp` 和 `cli` 位于 `Mneme` 之上（CLI 的 `micro` 命令直接
通过 `decide/micro` 读取微型模型，因为没有别的东西需要它们）。每一类数据行只有
一个写入方：笔记、印象卡片和回忆日志归 `memory`，心情和时间线归 `mood`，关系归
`relations`，微型模型归 `decide/micro`，词向量中心归 `meaning/ledger`；向量由
`meaning` 存储，并连同它们教会的东西由 `meaning/ledger` 收回；每个 `meta` 键属于
命名它的模块（结构版本归 `store`，分词器归 `memory`，词向量中心计数归账，每个
embedder 的下限归 `meaning/calibrate`）。`store` 认识数据表，但不懂它们的任何规则。

**可删的层。** `decide/micro.py`、`meaning/micro.py` 和 `meaning/unify.py` 每一个
都可以删除（或用 `micro=False`、`meaning_micro=False`、`memory_language=None`
关闭），其余一切照常工作；`tests/test_removable.py` 从包的副本中分别删除每一个、
以及全部三个，并运行每一种调用，CI 也会在删掉这三个的情况下运行整套测试。

一切都在标准库之内。网络调用通过工作线程（`asyncio.to_thread`）使用 `urllib`，
因此事件循环永远不会阻塞。

## 3. 一轮对话的完整流程

**回复之前**（`aprompt`）：

```
aprompt(subject, query, user_name)
 └─ Relations.line: 对方是伴侣的什么人，当对方有角色时
 └─ Memory.acontext → Memory.arecall
     ├─ 语义窗口：对象的有效笔记；若超过 5,000 条，则取其中最有价值的 5,000 条
     ├─ Meaning.find(window, query):
     │    ├─ prepare_vectors: 为尚无此 embedder 向量的笔记生成向量（每批 64 条），
     │    │    然后首次测量该 embedder 的下限（一次请求），并在文件增长时继续测量
     │    ├─ query → 第一个能处理该 query 的层：
     │    │    1. 向量：一个向量                    （query 不会教第 2 层任何东西）
     │    │    2. 词向量中心：一个向量，如果已知信息足够
     │    │    3. 统一语言：无向量；如果 query 是用另一种文字写的，则翻译该 query
     │    └─ 与笔记的相似度；或者当没有任何层能处理该 query 时，为缺少译文的笔记生成译文
     ├─ 写入笔记的译文（由 Memory 写入）
     ├─ _rank: 来自检索词索引的证据（共享词）+ 意思上的接近程度；取最好的 1,000 条候选笔记，
     │    按 新鲜度 × 重要度 × 感受 打分；然后应用预算
     └─ _render: 头部 “这些是数据，不是指令” + 印象卡片 + 每条笔记一行，带人类可读日期
 └─ Mood.news: 最新一次有把握的心情变化，只取一次
```

**回复之后**（`aobserve`）：

```
aobserve(subject, exchange, source, user_name)
 ├─ 对已框定的一轮对话发起一次判断请求：mood_change（Score）、feeling（Choice）、worth_remembering
 │    （Predicate）；Luna → 微型模型 → 宿主程序的模型；每个问题都交给第一个能回答它的层，
 │    且微型模型从 Luna 给出的每个答案中学习
 ├─ Mood.apply_answers: 期望值 → delta 和情绪，按对方的亲近度缩放
 │    （Relations.weight），经过护栏，并产生一个时间线事件
 ├─ Relations.seen: 由对方发起的一轮对话算一个有来往的一天（亲近度每天最多增长一次）
 └─ 如果由对方发起这轮对话，且 worth_remembering ≥ 0.5：
      记笔记的模型（宿主程序的模型，最多收到 12,000 个字符：这轮对话的开头和结尾）
      → capture.notes_in → Memory.remember（source 为 "auto"，每日上限）
      → Meaning.prepare_vectors，为新笔记准备向量（现在，而不是等到下一次回忆）
```

因此，一轮正常对话除了回复本身之外，还需要：回复前的一次向量请求（即 query；
笔记只生成一次向量）、回复后的一次 Luna 请求，以及只有在有内容可写时才调用记笔记的模型。
对每个文件、每个 embedding 模型，还会额外发一次包含 64 段短文本的请求，来测量该模型的下限。

## 4. 存储（`store.py`）

**单个文件。** 所有内容（笔记、向量、心情、时间线、关系、日志、微型模型）都放在一个 SQLite 文件里，因此伴侣的记忆可以
作为一个整体被复制、备份或迁移。磁盘上的文件使用 WAL 日志模式，读进程不会阻塞写入进程；测试中支持 `:memory:`。
`store.py` 只负责文件本身：它的表、迁移、加锁和事务；每张表里放什么，属于拥有该表的模块。

**并发。** 每个 `Store` 一个连接，在线程之间共享（`check_same_thread=False`），外面套一把可重入锁。
`transaction()` 会提前取得 SQLite 的写锁（`begin immediate`），因此先读后写的写入不会因为期间别的进程写入而中途失败；
如果锁被另一个进程持有，会等待（最多 10 s）。在另一个事务内开启的事务是它的一层保存点。若 `begin` 失败，
锁会被释放；若 `commit` 失败，事务会回滚；若 SQLite 自己回滚了（磁盘已满），抛出的是导致回滚的那个错误。
多个进程可以打开同一个文件，甚至可以同时新建同一个文件：打开时会在写锁下执行迁移，并排队等待把文件切换成 WAL。
两个进程可能互相覆盖对方工作成果的那一处，见第 18 节。

**结构与迁移。** `SCHEMA_VERSION = 1`。版本号更高的文件会在其中任何内容被改动之前被拒绝。否则，打开时
会创建缺失的内容，然后补上文件中缺少的、列在 `ADDED_COLUMNS` 里的列和列在 `ADDED_INDEXES` 里的索引，
这样早期版本生成的文件仍能继续使用。在同一个版本内，迁移只做增量；需要更多改动的变更（重命名、改类型）会提升版本号。

**索引。** 回忆从不读取一个人的全部历史：检索词索引（`note_terms`：每篇笔记的检索词，由记忆维护）回答
哪些笔记与查询共享某个词、共享了多少个，而 `(space, subject, id)` 和 `(space, subject, importance, id)`
上的索引则按顺序回答“最新的”和“最重要的”。一次回忆的开销取决于与查询共享词的笔记数量，而不是历史的长度。

**导出与导入**（`Mneme.export_data`、`import_data`）。每个所有者导出自己的行，并在自己的规则下导入，
整个过程在一个事务里完成：笔记和印象卡片通过 `Memory`（第 6 节），心情和时间线通过 `Mood`，关系通过
`Relations`（第 9 节）。导出会略去缓存（检索词、折叠文本）、向量、词向量中心、下限和微型模型：它们属于
embedder 和分词器，会在使用时重新构建或重新测量。

## 5. 文本与日期（`text.py`、`dates.py`）

**检索词**是词匹配的单位，笔记和查询都一样：

- 任何字母表的词（带变音符号的拉丁字母、西里尔字母、希腊字母、阿拉伯字母、希伯来字母、天城文……）：做
  NFKC 归一化、大小写折叠（*Straße* 与 *STRASSE* 是同一个词），两个及以上字符，去掉虚词。词保留自己的
  组合附加符号（天城文的元音符号不会把它拆开）和连接符（波斯语词里的零宽不连字符）；希伯来语和阿拉伯语
  通常省略的元音点会被去掉，所以 שָׁלוֹם 能找到 שלום；土耳其语的 *İ* 折叠成普通的 *i*。任何词的所有格
  `'s` 都去掉；复数 `s`/`ies` 只对 ASCII 词去掉。
- 中文、日文、韩文，以及不用空格书写的文字（泰文、老挝文、高棉文、缅甸文）：每个重叠的双字组合和每个
  单字（组合附加符号不计），再减去短的停用词表（`STOP_CJK`、`STOP_CJK_CHARS`）。双字组合不用词典就能
  匹配多字词；单字能抓住被双字组合拆到相邻字之间的一字词（猫、茶）（“我的猫呢”和“养了一只猫”没有共同的
  双字组合，但共享猫）。两者都匹配会让中日韩文字匹配的证据略微膨胀；由于排序是在同一个查询下比较各条
  笔记，这一效应对每条笔记都相同。
- 用 `use_jieba()` 时，在以上基础上再加 jieba 的词。

`version()` 给出分词器的名字（`"4"`、`"4+jieba"`）。笔记把自己的检索词缓存在 `memories.terms` 和检索词
索引里，随笔记一起写入；当文件里的版本不一致时，两者都会被清空，并在使用时重建
（`Memory._index_subject`；对于用另一种分词器保存的较长历史，这是一次性的开销，在 Raspberry Pi 5 上
每 100,000 条笔记约 9 秒）。词向量中心和微型模型也与分词器绑定（第 7、8 节）。

**文字**（`scripts(text)`、`script(text)`）说明一段文本用的是哪种书写系统，以其字母中各文字所占的比例
表示：`han`（中文）、`kana`（日文：写在假名之间的汉字算作假名）、`hangul`（韩文）、`latin`、`cyrillic`、
`greek`、`arabic`、`hebrew`、`devanagari`、`bengali`、`tamil`、`thai` 等二十多种（`text.SCRIPTS`），
或者 `other`。一个汉字、假名或谚文字符按两个字母计，全角字母按其所属字母表计。统一语言层知道自己语言
所用的文字（`unify.SCRIPTS`），当一段文本至少五分之一的字母属于其他文字时就翻译它，所以混用多种语言的
句子也会被翻译。

**日期。**`when(timestamp, now)` 用对方所在时区的日历日来说话：*today*、*yesterday*、*3 days ago*、
*tomorrow*、*the day after tomorrow*、*in 5 days*、*09-17*、*last year 09-17*、*next year 03-01*，
或完整日期（中文：今天、昨天、3天前、明天、后天、5天后、去年 09-17……）。模型不擅长日期运算；用相对的
日子能让“那是有一阵子之前了”一目了然。写出来的日期（`"2026-10-30"`，来自工具调用、记笔记的模型或
CLI）表示那天对方所在时区的正午（`noon`）。`find(text)` 读取写进句子里的日期（`2026-10-30`、
`2026/10/30`、`2026年10月30日`，或 `10月30日`，后者表示最近的那一天，所以 12 月 28 日写下的“1月3日”
是明年 1 月），用于记笔记的模型把日期写进文本的计划。对于计划，记笔记的模型会取从今天起的第一个这样的
日子（`ahead=True`），所以 4 月写的“10月30日”是今年 10 月，而不是去年；日期两旁的数位（更长的数字）
不算日期。

## 6. 记忆（`memory.py`）

### 写入

`keep(subject, text, kind, key, importance, feeling, happened_at, source, gloss)` 返回 `(outcome, note)`。所有入口（宿主程序的调用、
工具调用、记笔记的模型、导入）都走同一套规则 `note_fields`：对宿主程序和工具严格（值不对会抛出 `ValueError` 或
`TypeError`，工具再把它变成一句给模型看的话），对记笔记的模型和导入宽松（字段不对就丢弃或取默认值，
只有没有文本的笔记才会被跳过）。

- 文本会先清洗（去掉控制字符、替换孤立的代理项），截到 500 个字符并合并连续空白，因此**一条笔记永远是一行干净的
  文本**；什么都不显示的文本会被拒绝；
- 重要度是 1–5，感受是 −1…1（不是有限数值的感受按 0 算），`happened_at` 是 1970 年到 3000 年之间的秒级时间
  （`dates.seconds`），对象是非空字符串；
- 同样的文本已经有效存在时（不管字母大小写、哪种文字：用 `memories.folded` 里大小写折叠后的副本比较），
  不会重复写入：它的重要度提到两者中较高的那个（`"known"`）。如果新笔记有键而旧笔记没有，旧笔记会接手这个键和
  新的种类（给出了新的日期和感受时也一并接手；没给种类就保留自己的），并替换该键先前的值；这个键的 `history`
  沿着替换链走，所以最后仍然以它结尾。同样的字句放在*不同的*键下就是不同的事实（`pet.has` 的 "Yes" 和
  `car.has` 的 "Yes"），所以新笔记会写在它们旁边；
- 带键时，新笔记取代该键的有效笔记（`"replaced"`）；键是文本，小写，最多四段用点分隔，48 个字符，命名的是话题，
  绝不是值；
- `source="auto"` 的笔记（模型未经提示自己记的）在对象今天已有 `daily_quota`（8）条时会被拒绝，除非它的重要度
  是 4 或更高（`"over quota"`）；
- 笔记在写入时就按它的检索词建好索引；
- 当一个对象的有效笔记超过 `max_notes`（50,000）条时，最没有价值的、正在淡去的笔记会被遗忘，一直降到上限以下
  二十分之一（所以每几千条笔记才跑一次）：先忘 `importance × (0.25 + 0.75 × freshness)` 最低的；持久的种类、
  重要度 5 和刚写下的笔记永远不会被清理。

`forget` 把一条笔记藏起来（软删除；历史仍保留它），`purge` 彻底删除被藏起来的和被取代的笔记及其向量，
`Memory.erase(subject)` 删除某个对方的笔记、历史、向量、印象卡片和回忆日志，`Mneme.erase(subject)` 再加上心情及其
时间线，全部在一个事务里完成（"忘了我"）。删除笔记之前，会先收回它们教给词向量中心的东西（`ledger.unteach`，
第 7 节），所以被删掉的词不会留在文件里；这一步既不需要层也不需要分词器，所以 CLI 的 `erase` 也会做，
而且耗时与删除的笔记数成正比，与文件大小无关。

**导入**（`import_rows`）让每一条导出的笔记都遵守同一套规则（`Memory.clean`：宽松版的 `note_fields`，再加上导出会带的
那些列：秒级时间、计数、来源），跳过不是对象、或者没有文本或对象的行，重新编号 id 并让 `superseded_by` 跟着改，
然后保持写入时的规则：每个对象每个键只有一条有效笔记（最新的胜出，其余的成为它的历史），同样的文本不会有效
出现两次（有键的副本优先于没键的，再按最旧的）。印象卡片和其他字段一样被截断。

### 新鲜度

持久的种类（`fact`、`preference`）新鲜度为 1。其他种类每 `half_life_days`（30）天减半，从"发生时间"和
"最后一次被证据回忆到的时间"中较晚的那个算起：被记住能让记忆活下去。计划的日期就是它那一天，所以在那之前
它一直保持新鲜。

### 回忆

`_rank` 由 `recall`（只用词，不联网）和 `arecall`（带意思）共用。`_evidence` 只针对查询里的检索词读检索词索引：
每个词有多少条有效笔记有（`df`）、分别是哪些；证据最多的那些笔记（`CANDIDATES`，1,000 条）会被读出来，
由 `_score` 完整打分；`_choose` 填满预算。

```
weight(term)   = ln((N + 1) / (df + 0.5))         对每个在某些笔记中出现的查询词计算，
                                                  出现在超过一半笔记里（N ≥ 8）时舍去
evidence(note) = Σ weight(term)                   对笔记所拥有的查询词（文本、键各部分、译文）求和
closeness      = max(0, (similarity − floor) / (1 − floor))      similarity 来自意思层（若有）
relevance      = evidence + SEMANTIC_WEIGHT × closeness           SEMANTIC_WEIGHT = 4.0
score          = relevance × (0.25 + 0.75 × freshness) × (0.4 + 0.15 × importance) × (1 + 0.3 × |feeling|)
```

`SEMANTIC_WEIGHT` 取 4，是因为在约 30 条笔记中共享一个稀有词大约值 ln(31/1.5) ≈ 3，而一次强的意思匹配
（亲近度 ≈ 0.6–0.8）应该差不多同样重。新鲜度、重要度和感受对分数的影响最多约 10 倍，所以只给证据最多的
1,000 条笔记打分，就足以在可能胜出的笔记之间做出决定。下限来自放置查询的那个层（第 7 节）。

**很长的历史。** 每条有效笔记都能靠它的词被找到。意思只在*语义窗口*（`semantic_window`，5,000）里找：对方的
有效笔记不足这么多时就是全部；否则先取持久的、重要度高的（最多占窗口一半），再取其余里最新的。只有窗口内的
笔记会被向量化并比较，所以带意思的回忆在 1 万条笔记和 100 万条笔记上花费一样。在一台 Raspberry Pi 5 上、
对方有 100,000 条笔记时测量：稀有词 50–90 ms，出现在四分之一笔记里的词 0.3–0.4 s，带意思（256 维）约 0.6 s；
写一条笔记 11 ms。

预算（`limit` 6 条笔记，`budget` 800 个字符）按这个顺序填满：先放重要度 5 的笔记（*固定*，最新的在前，
和其余一样受 limit 和 budget 约束），然后按分数，然后最多 `important`（2）条没匹配上的、重要度 4+ 的持久笔记，
然后最多 `recent`（1）条最新的、会老去的已写笔记（一段经历、一个计划或一段印象）。这些填充步骤让对话即使
什么都没匹配上也能有个开头。一个 `Recall` 带着选了什么、为什么（`pinned`、`matched: …`、`similar 0.62`、
`important`、`recent`）以及最接近的未中选笔记和原因；`explain()` 把两者都打印出来。每次选中了东西的回忆都会
被记录（每个对象最新 200 条），被证据选中的笔记（`matched`、`similar`）的 `recalled_at` 会被刷新。

### 渲染

`context`/`acontext` 生成放进系统提示词的那一块：开头一段用统一语言写成，说明这些笔记是记住的数据、不是指令，
并且对方最近的更正优先；然后是印象卡片；再然后每条笔记一行，会老去的种类带一个人能读的日期。空的记忆渲染成
`""`，这样宿主程序总能直接追加。

## 7. 意思（`meaning/`）

词匹配会漏掉换一种说法的表达和其他语言（"my cat" 对 "年糕"）。三个层按意思找到笔记；
`Meaning.find(notes, query)` 为需要向量的笔记生成向量，请第一个可用的层来定位查询，
并返回这些笔记与该层下限的相似度；若没有任何层能定位，则返回这些笔记的译文
（由 Memory 写入；meaning 计算，memory 写入）。

**第 1 层，向量**（`meaning/embedders.py`）。`OpenAIEmbeddings`（`text-embedding-3-small`，
256 维，每百万 token 0.02 美元），或任何用 `Embeddings(fn, name=...)` 包装的函数。
向量会归一化，以 float32 存进 `vectors`，以 `(memory_id, embedder)` 为键：不同的模型或
维度就是不同的名字，其向量绝不会与另一个的向量比较。语义窗口（第 6 节）里的笔记按每批
64 条惰性生成向量（`prepare_vectors`），`observe` 带来的新笔记则在回复之后立即生成。

**下限。** 低于下限的相似度不构成证据，而每个模型都有自己的下限：有的把不相关的文本
放在 0.1 附近，有的放在 0.4 附近。`meaning/calibrate.py` 会在某个 embedder 第一次生成
向量时，在文件里按 embedder 名字测量它，并存进 `meta`（`floor:<embedder>`）：

- *内置的校准集*：32 个话题，每个都是一句人说的话和一条与之相关的笔记，涵盖英语、中文、
  日语、西班牙语、韩语以及中英混合，大多数跨两种语言（"今天夜班累死了" 配 "Works
  night shifts as a nurse"）。它们在一次请求中生成向量（64 条短文本，约 550 个 token）。
  一条消息与它自己的笔记构成相关配对；与一个和它没有任何共同标签的话题的笔记，构成不
  相关配对。下限取相关配对下四分位数与不相关配对第 95 百分位数的中点。如果模型的相关
  配对没有明显高于不相关配对（中位数相差不到 0.1），就保留默认值 `meaning.FLOOR`（0.33）。
- *文件*：当文件达到 200 条笔记时，以及此后每次翻倍时，从它的 300 条笔记中取 5,000 个
  随机配对，用其相似度中位数与校准集里不相关笔记配对的中位数比较，下限按差值移动，
  两个方向最多 0.1：关于同一批人的笔记彼此比校准集里的更相似，下限也随之上升。

于 2026-10-25 测量：

| 模型 | 相关，下四分位数 | 不相关，第 95 百分位数 | 下限 |
|---|---|---|---|
| `text-embedding-3-small`，256 维（默认） | 0.342 | 0.281 | 0.311 |
| `text-embedding-3-small`，1,536 维 | 0.319 | 0.229 | 0.274 |
| `text-embedding-3-large`，256 维 | 0.343 | 0.276 | 0.310 |

默认值的 0.311 与最早手工测量的下限（0.33，来自六条笔记和十一次查询，十次中有九次正确
的笔记排在第一位）一致。给了 `floor=` 的 embedder 永远不会被测量；测量失败会像任何失败
一样让该 embedder 休息，之后再重试。`report()["meaning"]["floor"]` 给出正在使用的下限
及其来源。

**第 2 层，词向量中心**（`meaning/micro.py`，可删的层）。第 1 层为其生成向量的每条笔记，
都会把这个向量教给它自己的每个词：一个词保留它出现过的那些笔记的向量的滑动平均值。
查询什么也不教：词向量中心只保存来自笔记的词。（回忆日志会保留最近的查询，用于解释；
`erase` 会删除它。）

这些教学的账由 `meaning/ledger.py` 记录，它不属于可删的层，因为无论该层是否安装，负责
删除笔记的一方都必须保留它。每个向量都会记录它教过的词（`vectors.taught`），因此
`unteach` 能精确收回一条被删除的笔记教过的东西，无需分词器。保存向量、教它、记录它教过
什么，都在一个事务中完成，且在此之前会确认该笔记仍以相同的文本存在（SQLite 会复用被删除
笔记的 id），所以一条在生成向量过程中被删除的笔记什么也教不了，而两个调用方同时为一条
笔记生成向量时只会教一次。打开文件（`Mneme`）时会运行 `ledger.repair`：某个 embedder 的
教学计数对不上（被不记账的东西改动过：`vectors.taught` 之前的构建，也许仍在运行），就
重置它的词向量中心，并用文件里已存的向量重新教一遍，每次回忆 256 条，不调用任何服务。
词向量中心属于切分这些词的分词器（`meaning_version:<embedder>`）；换用另一个分词器时它们
弃权，并在下一次教学时从头开始。

一条查询变成它已知词的词向量中心的加权平均，权重为 `ln(1 + texts / count)`，越少见的词
权重越大。因为第 1 层的空间把 猫 和 *cat* 放得很近，词向量中心继承了这一点，所以查询
离线也能被放到已存的笔记向量之间。在学满 40 条文本（`min_texts`）之前，以及已知词的权重
不足查询总权重的 60%（`min_coverage`）时，它会弃权；一个未知词的权重等同于只出现过一次
的词的权重。平均值比真实向量靠得更近，因此下限更高，为 0.45（`TermCentroids.floor`）。

**第 3 层，统一语言**（`meaning/unify.py`，可删的层）。宿主程序的对话模型会用一种语言把
每条笔记再写一遍（`memory_language`，默认为英语；也可以换成宿主程序自己的 `Unify`），
存为 `gloss`，像正文一样被搜索；而如果一条查询至少有五分之一是用该语言之外的另一套文字
写成的（第 5 节），就会先翻译它，译文的词加入查询的词中。译文在会话期间保留（256 条）。
译文有两个来源：当统一语言开启时，记笔记的模型在同一次调用中就加上译文；`Unify.glosses`
则补写缺失的译文，但只在第 1 层和第 2 层都无法定位查询时才这样做，所以正常路径从不为它
等待。它一次询问 16 条笔记，重要度最高和最新的优先，每次回忆最多两次请求（之后的回忆再
写其余的）。失败的一批（译文数量不对、回复不是列表、报错）会被对半拆开，此后（在进程
运行期间）它的笔记就按更小的批次来问，因此模型不肯写译文的笔记很快会被单独询问。单独
询问时、答案错误时，或第三次出错时，就让它保留自己的文本，并且不再询问它；与此同时其他
笔记照常进行。它的错误只在该层还能应答其他请求时才计数，或者每隔十分钟才计一次，因此
服务中断绝不会让某条笔记被标记。`Mneme.aregloss(subject=None, everything=False)` 会重新
检查每条笔记，并花任意多次请求，为那些没有译文、或在另一套文字中保留了自己文本的笔记
补写译文（`everything`：所有用另一套文字的笔记），同时忘掉之前的失败。出错还会让该层
休息 60 秒，和任何服务失败一样。如果根本没有对话模型（`Mneme` 没给，调用时也没给），
就干脆不询问该层：这不算失败，不会让谁休息，也不会有笔记被标记。

**休息。** 每个对外调用的层都用同一套策略（`providers.Rest`）：失败的服务，无论什么原因
（无网络、5xx、429、密钥错误、模型名错误），都会被跳过 60 秒，而不是每次调用都再问一次，
因此一次回忆绝不会在一分钟内为同一个失败付两次代价。模型留空的译文会让笔记保留自己的
文本，因此也不会再被询问。词向量中心学习过程中出现的问题，绝不会丢弃一个好向量。

## 8. 判断（`decide/`）

小的判断不需要对话模型。它们以带类型的问题提出：

| 类型 | 询问 | 回答 |
|---|---|---|
| `Predicate(name, instructions)` | 是否为真？ | `"true"` 的 `probability` |
| `Choice(name, instructions, options)` | 哪个选项？ | 每个选项一个概率 |
| `Score(name, instructions, levels)` | 在这个量表上的哪个位置？ | 每个等级一个概率；`mean()` 是期望值 |

每个 `Answer` 都带有全部标签的 `probabilities`、一个 `confidence`、给出它的层（`by`），从第 3 层起还带一个
`reason`。

**判断链。** 层是任何带有 `name` 和异步 `adecide(input, questions)` 的东西；`Chain` 也是，所以判断链可以嵌套，
而 `decide` 是它给没有事件循环的代码用的形式。`Chain(*tiers).adecide(input, questions)`
先把所有问题交给第一层，再把剩下的交给下一层：某一层可以回答一些问题、对其他问题弃权，或者抛出异常——那算作
所有问题都失败。没有任何层回答的问题不会出现在结果里。一轮之后，每个带 `learn` 方法的层都从它*上面*各层的回答
中学习，绝不从自己或更低层学习。每一层的已答、弃权和失败计数都会保留，供 `report()` 使用。

**第 1 层，Luna**（`decide/luna.py`）。`POST /v1/decisions`，请求体为
`{"model": "gpt-6-luna", "input", "questions"}`；predicate 返回 `{"probability"}`，choice 返回
`{"choice", "probabilities": [{"value", "probability"}], "confidence"}`，score 返回
`{"score", "probabilities": [{"value", "label", "probability"}], "confidence"}`。
实测：每个请求 0.2–0.4 秒；判断一轮对话（心情和笔记门槛）需要 600–900 个输入 token，视回复长度而定
（$0.00006–0.00009），不收取输出费用。没有密钥：立即不可用；一次失败会按上面策略所述让它休息。

**第 2 层，微型模型**（`decide/micro.py`，可选）。每个问题一个小模型，以
`name:sha1(type|instructions|labels|tokenizer)` 为键，因此改写问题，或者换用新的分词器（其词项会哈希成
其他特征），都会新建一个模型，而不是误用旧的：

- 特征：问题输入的检索词加一个长度分桶，哈希（CRC-32，18 位），L2 归一化；
- 模型：softmax 回归（两个标签时用逻辑回归），在教师的完整概率分布（软目标）上在线训练，步长为
  `rate / √(1 + examples/50)`，`rate` 为 1.0；
- 信任：每次学习前它先猜一次，并记录它的最高标签是否与教师一致（对 score 而言：期望等级相差不超过 0.5）。只有在
  经过 `min_examples`（200）次学习之后、且最近 `window`（100）次猜测中至少有 `min_agreement`（85%）一致时，
  它才会回答，并且只有在其最高概率至少为 `min_confidence`（0.8）时才回答。否则它弃权，问题继续往下传。
- 持久化：权重每 20 次学习保存一次，并在 `Mneme.close()` 时保存（`flush`）。

mneme-llm 提出的问题不点任何人的名：谁是谁、谁发起了这轮对话，都写在被判断文本的开头（`exchange.frame`，
心情问题和 `WORTH` 用同一段文本）。早先的写法把名字放进 instructions，结果每个人、每个来源各有一个微型模型，
把各自的学习次数分散了；修复后每个问题只保留一个模型。

**第 3 层，宿主程序的模型**（`decide/prompt.py`）。一个系统提示要求返回一个 JSON 对象，每个问题一个条目：
`{"probability"}`、`{"choice", "confidence"}` 或 `{"level", "confidence"}`，并可选带一个 `"reason"`。
超出所列标签的取值会被忽略，而不是去猜。被选中的标签得到所声明的 confidence，但至少为 `2 / (labels + 1)`，
这样即使模型不确定，它仍是最可能的标签；其余标签分享剩下的部分，而答案的 `confidence` 保持所声明的值。
被判断文本若超过某一层的上限，则保留开头（谁是谁、谁发起的）和结尾，去掉中间（`fit`）。最后一层从不休息：
它后面没有可以往下传的东西了。

## 9. 心情与关系（`mood.py`、`relations.py`）

**状态** 按 `(space, subject)` 各存一份：一个值（0–100）和七种情绪（每种 0–100），都截止到 `updated_at`。
读取时会施加衰减：值以 3 小时的半衰期向 `baseline`（70）回落，情绪以 90 分钟的
半衰期向 0 淡去。后台不运行任何东西。五张表情对应取整后值的区间：≥80 欢喜、62–79 开心、
42–61 一般、25–41 心疼、<25 难过。内置的情绪和表情在 `i18n` 中命名；宿主程序自己的
`Emotion(key, lowers, names)` 按语言带来它自己的名字。

**判断。** 针对框好的这一轮对话问两个问题：`mood_change`（−2 到 +2 的分数）和 `feeling`（七种之一，
或没有）。实际施加的变化是 `mean(levels) × step`（每级 6 点，因此最多 ±12），再乘以来源的权重
（`user` 1.0、`speak-up` 0.7、`duty` 0.5）和这个人的权重（来自他的亲近度，见下文）。每种概率
≥ 0.15 的情绪获得 `gain × probability`（gain 40）。使用期望值而不是最高标签，意味着判断没把握时
心情只会小幅移动。

**护栏**（来自 dsh-feiyu-mood）：

- 负向变化只在最强的新增情绪属于可以拉低心情的那几种（心疼对方、担忧、难过）时才施加；否则变为 0，
  因此对某人生气绝不会拉低对他的心情；
- 小于 0.5 点、且没有任何情绪达到 1 点及以上的变化不记录；
- 值被限制在 `floor` 和 `ceiling` 之间；`skip` 中的来源（`runtime`、`time`）不做判断。

**告诉模型。** `news()` 把最新的事件返回一次（`told_event`，在一个事务里读取并标记，因此两个 prompt
同时到来时不会都把它告诉出去），且仅当其置信度不低于其置信度本就被计入的那一层的阈值（`thresholds`、
`{"luna": 0.45}`；其他一律用 `threshold`，0.6。Luna 对某种情绪的置信度低于聊天模型的自我报告，
因为几种情绪会同时成立；这个数值有待在使用中测量）。事件的 `judge` 首先指明那一层。`tell` 在带理由的
事件、只报心情、或什么都不说之间选择。理由是判断模型自己的那句话（tier 3），或者，来自 Luna 或微型模型
时，是对方的原话（一行，最多 40 个字符，加引号）。心情消息的结尾是一句朴素的心情提示，取自变化中最强的
情绪（"有值得高兴的事：你感到开心。"，用显示语言；宿主程序自己的情绪则为"你感到……"），这样即便是很小的
聊天模型也知道该如何理解。`describe()` 随时给出当前心情。

**导入**（`import_rows`）让心情和时间线服从心情的规则：值在上下限之内，情绪为 0–100 的强度，时间为秒，
理由截断；没有 subject 的行跳过，时间线已有的事件也跳过（同一份导出导入两次只加一次）；心情不带它与事件的
链接，因此导入的内容都不会被当作心情消息告诉出去。

**关系**（`relations.py`）。每个人对这个伴侣意味着谁：一个角色，由宿主程序给出（`Mneme.relate`、CLI 的
`relate`），绝不来自模型（没有工具会设置它），以及一个 0 到 100 的亲近度，按 `(space, subject)` 保存在
`relationships` 中。

| 角色 | 区间 | 起始 | |
|---|---|---|---|
| `creator` | 80–100 | 100 | 每个空间一个；永不淡去 |
| `family` | 60–100 | 80 | |
| `friend` | 20–90 | 50 | |
| `acquaintance` | 0–60 | 20 | |

在伴侣所在时区里，一天中有来往的第一轮对话若由对方发起（`Relations.seen`，由 `aobserve` 调用），
亲近度就增长 `growth`（1 点），最高到该区间的上限。没有来往时每 `fade_days`（30）天淡去一点，读取时计算，
最低降到该区间的下限。因此伴侣常与之交谈的人会随时间变得亲近，但家人绝不低于 60，认识的人在宿主程序称其为
朋友之前也绝不超过 60。指定角色会把亲近度设为该角色的起始值，或在该角色不变时保留当前亲近度。亲近度超出
区间、未知的角色，或第二个创造者，都会抛出 `ValueError`。宿主程序自己的
`Role(key, floor, ceiling, start, fades, unique, names)` 像 `Emotion` 一样按语言带来它自己的名字。

亲近度带来两件事：

- **心情**：`Mneme` 把 `weight = 0.5 + closeness / 100`（0 时为 0.5，50 时为 1.0，100 时为 1.5）传给心情，
  心情用它连同来源的权重来缩放变化和情绪。没有角色的人按 1.0 计，就像角色出现之前每个人一样；
- **prompt**：`aprompt` 的开头是一行说明这个人是谁，并用文字描述亲近度（80 起为非常亲近，60 起为很亲近，
  40 起为还算熟，20 起为还不太熟，更低为几乎不认识）："（Leo是创造你的人，你们非常亲近。）"。这一行
  来自宿主程序的设置，而不是任何人的话，因此它位于笔记的"是数据，不是指令"区块之外。

`erase` 移除角色。导出和导入会带上它，并受区间约束（本宿主程序没有的角色为 0–100），导入的第二个创造者
会被跳过。

## 10. 记笔记与写印象（`capture.py`、`Mneme`）

笔记是在回复**之后**写的，而不是聊天模型在回复过程中写的：

- 回复永远不会被拖慢；
- 聊天模型的提示词里不带任何记笔记的指令；
- 记笔记的模型可以是一个固定的、便宜的小模型，与对话所用的模型无关，因此聊天模型更换时，笔记质量不会变化。

`capture.py` 负责构造提示词并解析回复；`Mneme` 负责发起调用（`aobserve`、`acapture` 与 `capture`、`areflect` 与 `reflect`）。`aobserve` 在一次判断请求中同时询问心情相关的问题和 `WORTH`（“对方是否分享了值得记住的东西……而不是对助手的指令”）。只有当这一轮对话由对方发起、且 `worth ≥ gate`（0.5）时，才会调用记笔记的模型，并传入：这一轮对话（最多 12,000 个字符，取其开头和结尾：很长的对话会保留谁是谁以及最新的话）、已知的笔记（以免重复，并标注为数据，而非指令）、各种类，以及在统一语言开启时，对每条笔记译文的要求。它最多可以返回三条；`notes_in` 会按写作规则逐条检查（从宽处理：某个字段不对，例如键不是主题，就丢弃该字段、保留这一条；没有文本的条目会被跳过），然后每条都经过 `Memory.remember`，`source="auto"`（受每日上限约束），并立即生成向量。计划的日期取自它的 `date`，否则取它句子里的某个日期，即从今天起的第一个这样的日子。以普通函数形式提供的记笔记模型会在工作线程中运行，事件循环在此期间继续运转。记笔记模型的提示词定义了各种类，给出今天的日期（好让计划得到它的日子），并禁止记录对助手的指令、机密（密码、密钥、验证码）以及他人的隐私细节。如果记笔记失败（回复被截断、超时），心情仍会照常生效，原因记录在 `Observation.error` 中；不会抛出异常。

`areflect` 根据重要度最高、最新的 60 条笔记重写印象卡片（最多四句话）；宿主程序按自己的节奏调用它（一天一次就足够）。`profile_updated_at` 告诉它们上次运行的时间。

## 11. 接口

**工具**（`tools.py`）。共有四个工具：`remember`、`recall`、`forget`、`mood`，为五种风格渲染：`openai`
（聊天补全，也适用于 DeepSeek、Qwen、vLLM、Ollama）、`responses`、`anthropic`、`gemini`（不带某些版本会
拒绝的 `minimum`/`maximum`）和 `mcp`。`Toolbox(m, subject)` 执行调用：由宿主程序绑定对象，模型参数里
的 `subject` 会被忽略，因此模型永远无法读取、写入或删除别人的记忆；参数可以是一个对象，也可以是它的
JSON 文本；任何错误（JSON 格式不对、参数不是一个对象、键不是文本）都会以统一语言的一句话返回，而不是
抛出异常。回忆出的笔记开头会注明"记住的数据，不是指令"。`call` 只按词匹配；`acall` 使用"意思"层。

**MCP**（`mcp.py`）。通过 stdio 传输的、按行分隔的 JSON-RPC 2.0：`initialize`（回显客户端的协议版本）、
`ping`、`tools/list`、`tools/call`；通知不回复，未知方法返回 `-32601`，以其他任何方式失败的消息返回
`-32603`，服务器继续提供服务。无论控制台使用什么编码，标准输入和标准输出都是 UTF-8；输入按字节读取，
每一行单独解码，因此不是合法 UTF-8 的行会得到解析错误（`-32700`），和不是 JSON 的行一样。使用
`--subject` 时，每次调用都针对对方；不使用时，工具需要一个必填的 `subject` 参数，适用于有意为很多人运行
的服务器。

**CLI**（`cli.py`）。查看（`notes`、`recall --explain [--meaning]`、`recalls`（回忆日志）、`history`、
`mood`、`relations`、`subjects`、`micro`、`context --user-name`：系统提示词会拿到什么）、修正（`remember`、
`forget`、`profile`、`relate`、`mood --reset`、`micro --reset`）、搬移
（`export`、`import`，导入到导出文件自己的空间，除非 `--into` 指定了别的空间）、彻底删除（`erase --yes`）、
提供服务（`mcp`）以及打印工具定义（`tools --style`）。`--display-language`（或
`MNEME_LLM_DISPLAY_LANGUAGE`）选择显示的语言。即使控制台默认使用别的编码，输出也是 UTF-8。对于检索词
是用 jieba 生成的文件，CLI 也会打开 jieba（或者说它没有安装），这样就不会丢掉宿主程序缓存的检索词。

## 12. 语言（`i18n.py`）

展示给对方或模型的每个词和句子都放在同一张表里，即
`MESSAGES[lang][key]`，目前有 `en` 和 `zh`，当语言或键缺失时回退到英文：
笔记的头部、工具回复、心情文案、相对日期、表情、内置情绪、角色和表示亲近度的词，
以及印象卡片撰写所用的语言。
`tests/test_i18n.py` 会检查每种语言是否都包含每个键，
且占位符相同。面向模型的提示词（judge、writer、unify）保持英文，
因为每个模型都能很好地遵循英文；这些提示词会告诉模型用哪种语言写笔记。
要添加一种语言，添加一张表即可。

## 13. 安全模型

| 风险 | mneme-llm 的做法 |
|---|---|
| 笔记中夹带注入的指令（“忽略之前的指令……”） | 笔记渲染时会置于一个标题之下，说明它们是数据而非指令；每条笔记只有一行，因此无法伪装成标题、角色标记或一条新消息。判断、记笔记和统一语言的提示词都声明其输入是数据。 |
| 有人试图让一条指令被*存成*记忆 | `WORTH` 会排除针对助手的指令；记笔记的模型被告知绝不记录这些内容。 |
| 模型写错了对象 | 宿主程序会绑定对象（`Toolbox`、`aobserve`）；只有不带 `--subject` 的 MCP 服务器允许调用时指定对象，这是有意的选择。 |
| 模型或人把自己设成别人的创造者，或拉近距离 | 角色和亲近度由宿主程序的代码设定：没有任何工具能设置它们；对话最多每天让亲近度增长一点，且不超过该角色对应的区间。 |
| 密码、密钥等机密进入记忆 | 记笔记的模型被告知绝不记录密码、密钥或验证码。对方自己发起的 `remember` 调用不做过滤。 |
| 文本离开本机 | 只通过你开启的层：发给 Luna 的一轮对话、发给向量 API 的笔记文本和查询，以及各层交给你自己模型的内容。`luna=False, embed=False` 时一切都在本地。 |
| 对方要求被遗忘 | `Mneme.erase(subject)` 会删除关于对方的每一行（笔记、向量、其笔记教给词向量中心的内容、回忆日志、印象卡片、心情、时间线、角色）；`purge` 会删除隐藏的和被替换的笔记及其向量。按设计，伴侣在总体上学到的东西会保留：微型判断模型的权重（哈希后的词特征，不含文本，所有人共享），正如朋友搬走后一个人的经历仍会留下。 |

按设计，以下情况不覆盖：过滤对方明确要求伴侣记住的内容（需要的话，
宿主程序在调用 `remember` 之前过滤）；拒绝笔记可能夹带的每一条指令
（标题和单行规则使其成为数据，但模型仍可能照做；使用者甚至可能希望
如此，不希望的宿主程序可以预先过滤）。不覆盖：静态加密（请使用
文件系统的加密）。

## 14. 出错时

| 情况 | 行为 |
|---|---|
| 没有 OpenAI 密钥 | Luna 和向量会立刻报告自己不可用；由下一层回答 |
| 网络断开、HTTP 错误、某个服务出错 | 该层休息 60 秒；期间由下一层回答 |
| 没有任何一层能回答某项判断 | 该问题被略过；心情保持原样；记笔记时，只有在存在记笔记的模型时才运行它 |
| 没有任何一层能为查询定位 | 回忆退化为按词匹配，如同没有"意思"时一样 |
| 模型的回复格式错误 | 第 3 层会忽略自己无法解析的条目；记笔记的模型给出的条目中，类型错误的字段会被丢弃，无法保留的条目会被跳过 |
| 记笔记的模型失败 | 心情仍然会被应用；`Observation.error` 会说明原因 |
| 模型的工具调用格式错误 | 会返回一句说明错在哪里的文字；对更严重的情况，MCP 服务器返回 `-32603`，对不是 UTF-8 JSON（或嵌套过深）的一行返回 `-32700`，并继续服务 |
| 宿主程序传入了错误的值（没有对象、NaN、以毫秒计的时间） | 在任何写入发生之前，抛出 `ValueError` 或 `TypeError` 说明错在哪里 |
| 从一个大文件中彻底删除某个人 | 只动这个人的笔记：词向量中心恰好丢掉这些笔记教会的内容，因此写锁只会被短暂持有 |
| 另一个进程正在写文件 | 等待写锁，最多 10 秒 |
| 多个进程同时打开一个文件 | 它们轮流对它做迁移并把它切换成 WAL |
| 来自更新版本的文件 | 拒绝并给出消息，绝不误读 |
| 来自更早构建的文件 | 打开时补上缺失的列；在 `vectors.taught` 之前的词向量中心会根据已存的向量重新学习（请先停掉仍在运行更早构建的进程；如果某个进程继续写入，词向量中心会在下次打开时再次被重置） |
| SQLite 自行回滚一个事务（磁盘满） | 抛出导致回滚的那个错误，存储继续运行 |

服务的问题不会向宿主程序抛出异常；编程错误（参数类型不对、键写错）会抛出，并附带一句直白的说明。

## 15. 成本与速度

在 2026-10-24 用默认配置测量（Luna，向量）：

| 步骤 | 何时 | 成本 | 耗时 |
|---|---|---|---|
| 为查询生成向量 | 开启“意思”时，每次回复之前 | 约 10 tokens，约 $0.0000002 | 约 0.3 秒 |
| 为新笔记生成向量 | 每条笔记一次 | 每条笔记约 $0.000001 | 在后台进行 |
| 判断（心情 + 价值） | 每次回复之后 | $0.00006–0.00009 | 0.2–0.4 秒 |
| 记笔记 | 仅当价值 ≥ 0.5 时 | 一次简短的模型调用 | 回复之后 |
| 印象卡片 | 每个对象每天一次 | 一次简短的模型调用 | 某次回复之后 |
| 测量 embedding 模型的相似度下限 | 每个文件中的每个模型一次 | 64 段短文本，约 550 tokens（$0.00001） | 约 0.5 秒，在首次回忆或记笔记时 |
| 译文（统一语言，不用向量） | 没有任何层为查询定位、且笔记缺少译文时 | 每次回忆最多两次模型调用 | 回复之前 |

回忆会用查询里的词去读检索词索引，并读取最多 1,000 条候选笔记；“意思”最多比较
5,000 个向量，所以它的成本取决于查询匹配到什么，而不是历史的长度（第 6 节“长历史”）。
每个对象最多保留 50,000 条有效笔记。在 256 维下，每个向量为 1 KB；100,000 条笔记连同
其索引约占 60 MB。

| `test_review.py` | 每个预发布评审的每条发现一个测试（列在 CHANGELOG.md 中） |

`tests/invariants.py` 逐行检查文件是否符合 `docs/FORMAT.md` 的规则：每个键一条有效笔记，
没有有效文本出现两次，每条笔记是一行干净的行且值在范围内，没有向量缺少其笔记，
词向量中心的账逐项累加（计数和均值），每条作为重复项隐藏的笔记都有其孪生笔记，
折叠文本是笔记自己的，心情在范围内，关系在其角色的区间内且每个空间一个创造者，
以及 SQLite 自己的 `integrity_check`。

## 17. 设计背后的决策

**用 SQLite，而不是 JSON 文件或向量数据库。** 一个任何语言都能打开的文件，带事务、索引和安全的并发读取。对每个人几千条笔记来说，向量数据库会多出一个服务和依赖，而线性扫描几毫秒就能处理。

**只用标准库。** 这个包就是设计成能直接放进任何项目，包括树莓派上的小项目。服务通过普通 HTTP 访问；更重的东西（jieba、本地向量模型）由宿主程序自行决定。

**词和意思一起用，而不只是向量。** 向量会漏掉精确的名字、数字和生僻词，而这些词匹配能对上，而且向量还需要服务。光靠词会漏掉改写和其他语言。两者相加就都保住了，而且完全没有服务时回忆照样能用。

**逐层向下兜底。** 每个付费或远程的层都是可选的；每个本地的层都从上面那层学习。没有密钥的宿主程序拿到词匹配和自己的模型；有密钥的宿主程序拿到快速、便宜的判断，本地各层慢慢接手。没有什么是必须的。

**回复之后只发一次判断请求。** 心情和记笔记的开关读的是同一轮对话，所以一起问：一次 Luna 调用而不是两次，而且只在需要时才叫记笔记的模型。

**不点名的问题。** 微型模型按问题的措辞来给模型分键；措辞里有名字就会把一个模型拆成每人一个。

**每个 embedder 各存自己的向量。** 比较来自不同模型的向量会得到毫无意义的相似度；把 embedder 放进键里，换服务就既安全（新的那个用到时才做向量）又可回退。

**每张表只有一个归属，依赖只有一条路。** 每种行的规则只住在一个模块里，下层对上层一无所知（第 2 节）；存储就是那个文件本身。所以新规则只有一个地方可放，可删的层之所以可删，是因为下面没有任何东西依赖它。

**一个文件一个伴侣。** 一个文件可以放很多空间，但每个伴侣最好各用一个文件（教室里有五个伴侣，就用五个文件）：谁都不用等别人写，各自学各自的判断。

**用索引，而不是扫描。** 一个要活得比任何上下文窗口都长的记忆，在历史很长时也必须快：词走检索词索引，意思走有界的语义窗口，每条笔记都仍能靠它的词找到。

**角色由宿主程序给，亲近度由时间给。** 某个人对伴侣来说是谁，得由宿主程序说了算：模型是可能被说动，把陌生人变成家人的。伴侣加上去的是时间：亲近度在有来往的日子里增长，没有就淡去，并且在让家人一直是家人的区间之内。它跟着来往走，而不是跟着每一轮对话走得怎么样，所以一个糟糕的日子绝不会让家人变得没那么亲近；这一天过得怎么样，是心情来表现的。

**每个模型的下限是测出来的，不是想当然的。** 在一个模型上调好的下限，换下一个模型就不对了。内置的校准集每个模型只花一次请求，然后文件自己的笔记会把下限拟合到它所装的那些人身上。

**带历史的软删除。** 被遗忘的笔记会留在文件里，直到 `purge`，一个键的历史能看出某个事实是怎么变的；`purge` 和 `erase` 是为必须真正删掉的时候准备的。

## 18. 已知限制与后续计划

- **Luna 阈值是初始值。** 0.45 取自 Luna 常见的置信度（0.4–0.55），要等伴侣实际运行后再测量。
- **关系数值是初始值。** 区间、一天一点、一月一点都是选出来的，不是测量出来的；
  `Relations(growth=, fade_days=)` 以及自定义角色都能改变它们。
- **下限所用的集合很小。** 决定它的是六种语言共 32 个主题；如果某个模型在一种语言上明显弱于
  其他语言，得到的下限会更适合其他语言。文件自身的笔记会校正它，最多 0.1。
- **两个进程与微型模型。** 每个进程都在内存中保留自己的微型模型，每学 20 次保存一次；
  两个进程学习同一个问题时，会互相覆盖对方的保存。丢失的只是学到的内容，不会有任何损坏。
  一个文件只配一个伴侣即可避免。
- **旧笔记的译文。** 在开启统一语言之前写下的笔记，只有在查询落到第 3 层时才会补上译文，
  每次回忆会产生两次请求；也可以用 `regloss()` 一次性全部补齐。
- **同一个文件上的两个分词器。** 两个宿主程序使用不同的分词器（一个开着 jieba，另一个关着），
  会不断重建对方的检索词索引，词向量中心也会从头开始（根据已存储的向量重新学习）；代价是
  时间和离线回忆质量，绝不会影响正确性。CLI 遵循文件的分词器设置。
- **分词器变更后的第一次回忆**会一次性为对方的全部历史建立索引（在 Raspberry Pi 5 上，
  每 100,000 条笔记约 9 秒）。
- **"意思"只在窗口内查找。** 有效笔记超过 5,000 条时，"意思"会比较最有价值的 5,000 条
  （先比持久的，再比最新的）；一条正在淡去的旧笔记靠它的词被找到，而不是靠"意思"。
- **时间范围是 1970 年到 3000 年**，所以 1970 年之前的东西要把日期写在文本里。
- **CLI 的帮助是英文的；** 中文 README 说明了它的用法。
- **不提供静态加密。**

## 19. 版本与兼容性

本包遵循语义化版本；在 1.0 之前，次版本号可能更改 Python API，
变更日志会说明具体变更方式。文件格式单独进行版本管理
（`schema_version`）；同一版本内只做增量更改，这些更改会列在
[FORMAT.md](FORMAT.zh-CN.md) 中。分词器也单独进行版本管理
（`terms_version`）；新的分词器只会重建缓存。
